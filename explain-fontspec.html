A focused explanation · renderer/font loading

Why data is not in FontSpec

TS2353 · excess property check

The Anton object is being placed in an array declared as FontSpec[]. But FontSpec describes a font file to locate, not a font already loaded into memory. TypeScript catches the shape mismatch at the object literal.

src/mastra/renderer/fonts.ts TypeScript 6.0.3 Satori 0.44.3 typecheck reproduces TS2353
01 · Architecture and data flow

Two distinct shapes are being mixed

The font loader has a metadata stage and a loaded-font stage. The error comes from putting a loaded-font-shaped object into the metadata stage.

FONT_SPECSFile descriptors: file name, family, weight
→ loader →
loadFonts()Joins each descriptor to the fonts directory and reads bytes
FontConfig[]Loaded records: family, binary data, weight, style

Then satori-renderer.ts calls loadFonts() and passes its result into Satori's fonts option.

02 · Root cause

The declaration and the object literal disagree

What the array promises

interface FontSpec {
  file: string;
  name: string;
  weight: 400 | 700 | 800;
}

const FONT_SPECS: FontSpec[] = [ ... ];

Each item must include file, name, and weight. No data or style property is declared.

What the Anton object supplies

{
  name: "Anton",
  data: new Uint8Array(
    fs.readFileSync("node_modules/@fontsource/anton/files/anton-latin-400-normal.woff"),
  ).buffer,
  weight: 400,
  style: "normal",
}

It has data and style but no file. It resembles a loaded font, not a file descriptor.

In plain terms: TypeScript is reporting the first extra key it sees, data. Fixing only that one diagnostic by adding data to FontSpec would not make this object compatible with the loader's actual expectations.
03 · Execution lifecycle

From declaration to where it fails

1
TypeScript contextually types the array literal.

Because FONT_SPECS is explicitly FontSpec[], every element is checked against that interface.

2
Excess-property checking examines the Anton literal.

data is not a known key on FontSpec, so tsc emits TS2353 on that property.

3
The loader assumes every spec has a path.
const abs = join(fontsDir, spec.file);
data = readFileSync(abs);
fonts.push({ name: spec.name, data, weight: spec.weight, style: "normal" });
4
Rendering never gets a well-defined Anton font.

Even if the type error were suppressed, the loader does not consume spec.data; it tries to join fontsDir with spec.file instead.

05 · Contracts and options

Choose which representation the list is meant to contain

ApproachRepresented dataWhat must happen
File-backed{ file, name, weight }Put Anton's WOFF at a known assets location, list its actual path/file name, and let the existing loader read it.
Inline bytes{ data, name, weight, style }Model separate file-backed and preloaded cases (for example a discriminated union), then branch in loadFonts() to use bytes directly or read the file.
Separate listsFile specs plus a preloaded font configKeep the current file loader simple, load Anton separately, and combine the resulting FontConfig[] before passing it to Satori.
Smallest conceptual correction: Treat the Anton object as a loaded font, not a FontSpec. Either put it in the final FontConfig[] path and skip file loading for it, or make the loader explicitly support both shapes.
06 · Critique and validation

Why the diagnostic matters beyond compilation

Compile-time bug

Confirmed: npm run typecheck -- --pretty false reports fonts.ts(37,3): error TS2353.

Potential runtime bug after a superficial fix

If data were merely added to FontSpec, the loop would still call join(fontsDir, spec.file). Since the Anton literal has no file, its loaded bytes remain unused and the runtime path is invalid.

Avoid: casting the literal to FontSpec, widening the interface without updating the loader, or silencing the error. Those only hide the mismatch; they do not wire Anton's binary into the returned FontConfig[].

The source currently imports fs and synchronously reads Anton directly from node_modules, while the established loader resolves a dedicated assets directory. That means bundling/deployment path behavior should also be considered when choosing the eventual fix. No source files were changed for this explanation.
